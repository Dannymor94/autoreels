# PLAN.md — Авто-Рилс: план реализации

Инкрементальный, каждый milestone даёт реальный выход до начала следующего. Стоп-чеки явные.

Стадии конвейера (R0–R4) — из `PROJECT_GUIDE.md`. Здесь — **порядок сборки**, который режет конвейер вертикальными слайсами.

---

## Решение: архитектура масштабирования отложена

Полноценная архитектура масштабирования **НЕ строится** до закрытия M1. Швы под масштаб заложены (граница облако/локаль, провайдер-абстракции, манифест-контракт, идемпотентность). Узкие места определяются на работающем конвейере с реальной пачкой видео, **не заранее**.

## M0 — Один клип end-to-end ✅ ЗАКРЫТ

Локальный файл → валидный вертикальный рилс с субтитрами. Каркас, извлечение аудио, транскрипция с кэшем, сжатие транскрипта, R0-выбор, нарезка с кропом, ASS-субтитры с burn-in, CLI-склейка — всё сделано и проверено на реальном материале.

## M1 — Полный R0 + качество отбора ✅ В ОСНОВНОМ ЗАКРЫТ

Сделано:

- **R0 recall** — over-generation с `candidate_multiplier`, ранжирование по score, top-N через `max_reels`, отсев в `<манифест>.discarded.json`.
- **Whisper-чанкинг** — аудио по ≤10 мин с VAD-границами, склейка word-таймкодов со смещением, укладка в лимит Groq 25 МБ.
- **R0-чанкинг** — токенный чанкинг транскрипта, overlap, дедуп по перекрытию диапазонов.
- **OpenRouter failover** — провайдер-пул с adaptive-стратегией, пинг-проверка на старте, исключение недоступных провайдеров с внятной причиной.
- **Кликбейт `title` + `description`** — рамка R0_SPEC §4 + few-shot.
- **R4 — snap границ** — притяжка к паузам и словам, punctuation-first снап конца.

Осталось в M1:

- **R2 — оркестрация + review-UI.** FastAPI + очередь + статусная модель (`awaiting_review`). React-экран: превью клипа, правка in/out, правка заголовка, approve/reject. Скилл `frontend-design`. **Это главный незакрытый пункт M1.**

## M1.5 — Качество клипов по смыслу ✅ ЗАКРЫТ

Отработка жалобы «много нарезок обрывается, мысль не закончена». Найдено и починено пять причин; результат замерен ручной разметкой на одном материале три раза.

| замер | чистых | приемлемых | брак |
|---|---|---|---|
| до работ | 3/20 | 3/20 | 85% |
| середина | 9/20 | 13/20 | 35% |
| после | 11/15 | 13/15 | **13%** |

Что чинилось:

1. **Дрейф конца.** `_prefer_longer_end` тянул конец до заполнения длительности — до +27 с за смысловую границу. Удалён. Снап конца теперь punctuation-first: первое слово с `.?!` после `r0_end`, окно `max_end_search_sec`, фолбэк на паузу.
2. **Обрезка длинных моментов с не той стороны.** Резался конец (где развязка), теперь режется начало. Конец назад двигается только если подрезкой начала не уложиться.
3. **Потолок длительности.** 59 → 90 с. Площадки допускают до 180 с, но вовлечённость падает раньше.
4. **Отсутствие пунктуации в транскрипции.** `initial_prompt` для Whisper поднял плотность знаков с 1.8 до 9.2+ на 100 слов. Промпт подаётся в каждый чанк.
5. **Утечка промпта в транскрипт.** Затравка попадала в вывод как услышанная речь. Промпт переписан как непродолжаемый + постфильтр совпадений.

Плюс: детерминированный `dangling_start` с ремонтом (сдвиг начала к границе предложения вместо отбрасывания), дедуп по перекрытию диапазонов, интервью-режим (`source_kind`) — границы по смене говорящего через тире и вопрос ведущего как вход клипа, обрезка висячих слов на хвосте.

**Ключевой методический вывод:** метрика качества считается сама — модель на этапе R0 сообщает `r0_start`/`r0_end`, и отклонение финальных границ от них есть мера брака. Ручная разметка нужна только для калибровки, не для мониторинга.

## Текущее ограничение: бесплатный тариф Groq

Несущий лимит — **OTPM (выход) = 1000 ток/мин**, не входной TPM 8000. Он не публикуется в документации и не виден в заголовках; найден прямым пробником (`scripts/probe_groq.py`).

Следствие: `max_tokens=900` ≈ 3 момента на ответ. Урожай определяется **числом запросов**, а не размером чанка — поэтому чанки держим мелкими (`r0_chunk_tokens` 1200).

- **Prompt caching** — не применим (Groq поддерживает только на GPT-OSS, и снимает вход, а упираемся в выход).
- **Обрезка системного промпта** — ~300-400 токенов входа, эффекта почти нет.
- **Платный Developer-тир** — снимает OTPM целиком, ~$0.17–0.55/мес при текущем объёме. **Запланирован к покупке; до тех пор работаем на бесплатном.**

## M1.6 — Детерминированный предотбор + ручной режим 🔄 В РАБОТЕ

Цель — снять с LLM всё, что считается кодом, укоротить её ответ, и дать человеку возможность заменить её решение своим, не ломая остальной конвейер.

### Почему

Один вызов R0 сейчас делает четыре вещи: находит момент, оценивает, пишет заголовок и описание. Ответ на момент — 200–300 токенов, значит `max_output_tokens: 900` упирает урожай в ~3 момента на запрос. Потолок определяется длиной ответа, а не качеством отбора.

Бо́льшая часть этой работы модели не требует: границы блоков видны по паузам и пунктуации, оргмусор снимается правилами, заголовок строится по шаблону `R0_SPEC` §4.

Модели остаётся один вопрос: **есть ли здесь законченная мысль и стоит ли её смотреть.** Этот же вопрос человек отвечает лучше — поэтому ручной режим равноправен автоматическому, а не костыль.

### Поток

```
сжатый транскрипт
  → нарезка на блоки-кандидаты                      [код]      ✅ этап 1
    → отсев мусора правилами                        [код]      ✅ этап 2
      → эвристический скоринг признаками            [код]      ⚠ этап 3, под вопросом
        → top-K на окно                             [код]      ✅ этап 3
          → ОТБОР:  LLM(оцени эти K) → {id: score}    [LLM]    этап 4
                    ИЛИ human review                 [человек] этап 4-alt
            → снап, дедуп, тримминг как сейчас      [код]
              → заголовки для выживших              [шаблон или LLM] этап 6
```

Два пути отбора взаимозаменяемы: дальше по конвейеру они дают одно и то же — список id блоков со score. Всё, что ниже, о них не знает.

### Состояние этапов

**Этап 1 — блоки. Закрыт.** Границы по паузе, абзацу, смене говорящего, терминальному знаку. PXL: 119 блоков, медиана 22.1с. Лекция: 32 блока. Команда `arl blocks` для инспекции.

**Этап 2 — отсев мусора. Закрыт.** Артефакты Whisper («Субтитры создавал DimaTorzok»), оргмоменты и промо, голова и хвост записи (по 30с), плотность речи, повторы. Прощания и приветствия детектируются по фразам, а не по позиции — позиционное правило срезало сильное финальное обращение. Смена говорящего внутри блока — флаг, не отсев: вопрос ведущего бывает хорошим входом в клип.

**Этап 3 — эвристический скоринг. Под вопросом.** Структурные признаки работают, но два из трёх эталонных клипов ручной разметки оказались на рангах 23 и 41. Подозреваемые — штраф по плотности речи (наказывает медленную речь, а у этого спикера сильные места звучат медленно) и несработавший признак «начало предложения» («И», «Из» в топ-15).

Решение по этапу 3 принимается **по измеренной корреляции** с ручной разметкой, а не по впечатлению. Корреляция близка к нулю → скоринг выбрасывается; отсев мусора и top-K по окнам остаются, они полезны сами по себе.

### Этап 4-alt — Ручной режим отбора

```
arl blocks --review <источник>     # пронумерованный список блоков в файл
<человек размечает>
arl blocks --apply review.md       # читает разметку, строит манифест
```

Выдача — текстовый файл, редактируемый в любом редакторе: номер, длительность, полный текст блока, пустое поле для оценки. Никакого UI на этом шаге; текст читается быстрее, чем смотрится видео, и потому ручной отбор здесь дешевле, чем на готовых клипах.

```
[ 12 ]  24.5s  score: __
Текст блока целиком…
```

Человек ставит число 0–100 или оставляет пусто (= не берём). Ни границ, ни заголовков — их ставит код и следующий этап.

#### Правила разметки

Чтобы оценки были воспроизводимы и годились как эталон для автоматики, они ставятся по одной рамке — рубрике `R0_SPEC` §2, сведённой к тому, что видно в тексте блока.

**80–100 — публикуем смело:**
- мысль начинается и заканчивается внутри блока, развязка есть;
- первая фраза понятна без предыдущего контекста;
- есть цитируемая фраза — то, что захочется пересказать;
- контринтуитивность, переворот ожидания или закрытая арка «вопрос → ответ».

**60–79 — годится:**
- мысль целая, но без яркого крючка;
- начало чуть вязкое, но смысл не теряется;
- содержательно, но обыденно по формулировке.

**Ниже 60 или пусто — не берём:**
- мысль оборвана или развязка осталась за пределами блока;
- первое предложение опирается на то, чего в блоке нет («поэтому», «он», «это вот»);
- оргмоменты, реклама, обращения к залу;
- перечисление без пуанта, длинный разгон;
- внутри блока меняется говорящий и это рвёт мысль.

**Отдельно:** блок, где сильная мысль явно продолжается в следующем, помечается `+` — код склеит их, если суммарная длительность укладывается в пресет.

#### Почему именно так

- **Одно число, а не категории.** Score сортируется и сравнивается с оценками модели напрямую, без перевода.
- **Пусто = не берём.** Размечать 119 блоков утомительно, если каждый требует решения; пустое поле как дефолт означает, что читать надо все, а заполнять — только стоящие.
- **Никаких границ руками.** Границы уже поставил код и проверил снапом; ручная правка таймкодов вернёт нас к тому, от чего уходили.

#### Что это даёт кроме клипов

Каждая разметка сохраняется как датасет: `{id блока, текст, признаки, score человека}`. На нём измеряется корреляция эвристики (этап 3), калибруется промпт модели, и со временем видно, можно ли доверять автоматике на этом материале. Сейчас такого эталона нет вовсе.

### Этап 4 — Короткий вызов LLM

Промпт меняется с «найди моменты» на «оцени кандидаты». На вход — пронумерованные блоки с текстом и таймкодами. На выход:

```json
{"scores": [{"id": "b07", "score": 84}, {"id": "b11", "score": 71}]}
```

Ни заголовков, ни описаний, ни таймкодов — границы уже известны коду. Ответ на 8 кандидатов ≈ 120 токенов вместо 900. Рубрика `R0_SPEC` §2 остаётся, меняется только формат ответа. Блоки, которые модель не упомянула, считаются отвергнутыми.

### Этап 5 — Кэш решений по блокам

`id` блока = хэш текста. Оценка кэшируется по `(id, версия рубрики, источник оценки)`, где источник — модель или человек. Человеческая оценка имеет приоритет и не перетирается моделью. Повторный прогон того же источника не зовёт ни модель, ни человека.

### Этап 6 — Заголовки отдельно

Только для клипов, прошедших отбор. Сначала шаблон по паттернам `R0_SPEC` §4 с подстановкой ключевых слов; один батч-вызов LLM на все выжившие — если шаблон даёт слабый результат. В обоих случаях заголовки перестают конкурировать за OTPM с отбором.

### Порядок работ

1. Решить судьбу этапа 3 по измеренной корреляции.
2. Ручной режим (этап 4-alt) — даёт рабочий результат сразу и производит эталон.
3. Короткий вызов LLM (этап 4).
4. Сравнить их на одном источнике: сколько совпадений, где модель расходится с человеком.
5. Кэш (этап 5) и заголовки (этап 6).

Ручной режим идёт раньше автоматического сознательно: без эталона мы не сможем оценить, стал ли короткий вызов лучше прежнего.

### Чего M1.6 НЕ делает

- не меняет `r0_chunk_tokens` — хватит крутить эту ручку;
- не ослабляет гейты и пороги;
- не трогает снап, дедуп, тримминг — они работают и замерены;
- не отменяет полной автоматики: ручной режим остаётся режимом, а не единственным путём.

## M2 — Приём по ссылке + стык с экосистемой

1. **Слой приёма (`ingest.py`)** — взаимозаменяемые доставщики (yt-dlp / HTTP / Tailscale / Syncthing / ручное копирование), каждый кладёт файл в `inputs/`. Ядро читает локальный путь и от доставщика не зависит. Привязка по `source` = имя + sha256. Загрузка с Я.Диска уже есть (httpx streaming + Range-resume).
2. **Перенос между машинами** — Tailscale либо Syncthing. Зафиксировать выбор.
3. **Контракт с SMM-постером** — манифест (`title`/`description`/хэштеги + mp4) → формат кросс-постера.

**Выход M2:** вставил ссылку → клипы ушли в SMM-инструмент. Петля экосистемы замкнута.

## Зависимости и риск

- Качество R0 — главный риск — снят до приемлемого уровня (13% брака), метрика автоматизирована.
- Основной незакрытый пункт — **review-UI (R2)**, без него нет человека в петле на этапе готовых клипов. Ручной режим M1.6 закрывает часть этой потребности раньше по конвейеру и дешевле.
- Пропускная способность упирается в бесплатный тариф; решается деньгами, а не инженерией.
