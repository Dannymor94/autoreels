## #7 — зависимость после ремонта ритма

- `leans_on()` (стр. 172–181) возвращает транзитивную цепь `refers` для `standalone:false`.
- `fit_rhythm()` (297–335) определяет сбой `rhythm_why`, сначала пробует соседей, затем выбрасывает **целый проблемный кусок**, если он не содержит `keep` и оставшаяся длительность ≥ min_sec (стр. 329–334).
- `keep` при вызове из `propose()` (около 1201) строится из `seed.id` и `clip[-1].id`; зависимости прочих оставшихся единиц явно не проверяются после удаления куска.
- **Гипотеза:** допустима последовательность, в которой одна удалённая мысль `#1` является `refers` для оставшейся `#3`, но её нет в `keep` и она в слишком коротком куске. Для helper-only контрпримера предложить `#1:5s`, `#3:30s`, разрыв >10s, `#3 standalone:false refers:1`, `keep={3}`; `fit_rhythm` может убрать `#1`. **Не заявлять CLI-эффект**, пока не доказан фактический вход такой комбинации через production `mixed`, `build_passage/add_payoff` и проверки до пула. Если сборка недостижима, отметить helper-only или NOT_REPRODUCED.

## #8a — добавление вопроса в конец

- В `fit_rhythm` (312–324) сосед подставляется по `topic`, `eligible`, расстоянию, продолжительности и занятости. Запрета `nb.role == question` в этой ветке нет.
- `build_passage` (408–413), наоборот, снимает вопрос с хвоста. Но `fit_rhythm` происходит **позднее**, поэтому прежняя проверка может оказаться устаревшей.
- `fix_open_end` (625–652) ориентируется на **тон последней фразы**, а не семантическую роль `question`.
- **Гипотеза:** короткий кусок после скачка удлиняется допустимым соседним вопросом и проходит интонационный тест как `final`. Нужна трасса: значения `rhythm_why` до/после, ID/role/refs добавленного соседа, итоговая `Proposal.pieces`, факт прохождения `fix_open_end`.

## #8b — поздний отказ после обрезки конца

- `propose()` запускает `fit_rhythm()` перед `context_start` и `fix_open_end` (примерно стр. 1209–1280).
- Затем `fix_open_end` может удалить хвостовые фразы.
- После ремонта `propose()` вызывает `rhythm_why()` ещё раз (примерно 1268), но **не** вызывает повторный `fit_rhythm`; при ошибке кандидат пропускается.
- **Гипотеза:** раньше валидный последний кусок после `fix_open_end` становится короче `settle_need * rhythm_tail`, и кандидат отсекается, хотя рядом есть допустимый сосед для восстановления. Для CLI-пути синтетическая просодия должна действительно пометить последнюю фразу `open`; прямой `end_tone=lambda` — только HELPER.

## Как избежать циклов M223/M224

1. **Сначала** mini-spike: убедиться, что изолированный `cmd_autocut(..., llm="none")` строит обычный `mixed`-пул с настоящими `sentences`, `alignment/prosody`, и пишет только во временный root. Одно доказательство реального entry point использовать для всех трёх кейсов.
2. Затем **три** детерминированных входа (A/B/C). Для каждого: статус `CLI_CONFIRMED | HELPER_CONFIRMED | STATIC_ONLY | NOT_REPRODUCED` сразу после прогона; никаких задним числом переименованных `PASS`.
3. Trace: ids, refs, `refers`, порядок, `keep`, `rhythm_why` до/после, итог `Proposal`, исключение валидацией. Отдельно `expected/actual`.
4. Два целевых повтора максимум — `handoff/m222/QA-STOP-RULES.md`. Невоспроизводимую через CLI гипотезу не «дожимать» фиктивным callback, а закрывать в реестре как ограниченную.
