# Audit: Groq 429 «на полной квоте» (remaining=8000, reset=1ms)

Probe: `scripts/probe_groq.py` (standalone, не импортирует pipeline). Прогон —
чистый, 70 с между запросами, оба провайдера. Модели взяты из `config/r0.yaml`
(`qwen/qwen3.6-27b`, `google/gemma-4-31b-it:free`).

## TL;DR — корень найден

Лимит, который нас роняет, — **НЕ** входной TPM 8000. Это отдельный, **не
выставленный в заголовках** лимит **OTPM (output tokens per minute) = 1000** на
бесплатном тире `on_demand`. Триггер — **`max_tokens` (выход)**, а не размер
промпта. Заголовки `x-ratelimit-*-tokens` (limit 8000) считают **входные**
токены — поэтому в 429 и стоит `remaining-tokens=8000, reset-tokens=1ms`: вход
никогда не был блокером, и по нему ждать нечего. У OTPM заголовка нет вообще.

Тело ошибки (дословно, первый чистый отказ, prompt~4000 + max_tokens=2048):

```
Request too large for model `qwen/qwen3.6-27b` ... service tier `on_demand`
on output tokens per minute (OTPM): Limit 1000, Requested 1010. The request's
expected output tokens exceed the enforced limit; reduce max_tokens (or the
request's expected output) and try again.
```

Это объясняет все четыре симптома, за которыми гонялись два дня:

| Симптом | Объяснение |
|---|---|
| 429 при `remaining-tokens=8000, reset-tokens=1ms` | Это **входные** TPM-заголовки. Вход не блокер → показывает «полно». OTPM отдельный, без заголовка. |
| Ожидание не помогает | Ждать сброса входного TPM бессмысленно — режет выходной OTPM, а он рулится `max_tokens`, не временем. |
| `r0_chunk_tokens` 4000→2500 не помог | Это уменьшает **вход**. Лимит — на **выходе**. Промах по оси. |
| «оценка размера где-то врёт» | Оценивали не ту ось. Вход мы даже слегка **завышаем** (безопасно). |

## Ответы на вопросы аудита

**Q: Наибольшая проходящая комбинация prompt + max_tokens?**
По входу упереться не удалось вообще: `max_tokens=8192` + промпт ~5000
(API prompt_tokens=4689) → сумма **12881** токена, **PASS**. Ограничение
целиком на стороне выхода: `max_tokens=512` (резерв < 1000 OTPM) прошёл **все 7
из 7** размеров промпта; `max_tokens=2048/8192` падают, когда оценка ожидаемого
выхода задевает 1000 OTPM. Практический вывод: **держать `max_tokens` заведомо
ниже 1000** (например 512) — 429 исчезает.

**Q: Насколько наша оценка токенов расходится с usage.prompt_tokens API?**
Мы стабильно **завышаем** вход на ~5–7 % (растёт с размером):

| our_est | API prompt_tokens | Δ |
|---:|---:|---:|
| 512 | 499 | +2.6% |
| 1012 | 965 | +4.9% |
| 2012 | 1895 | +6.2% |
| 3012 | 2827 | +6.5% |
| 5012 | 4689 | +6.9% |
| 6012 | 5620 | +7.0% |

Знак ошибки — консервативный (запас в нашу пользу). Гипотеза из комментария
`config/r0.yaml` («оценка мала → упираемся во вход») **неверна**: и знак не тот,
и ось не та.

**Q: Называет ли тело ошибки лимит, отличный от 8000?**
Да — **OTPM: Limit 1000** (не 8000, не per-request context cap). Плюс это
тир-специфично: `service tier on_demand`. На Dev-тире (платно) лимит другой.

**Q: То же ли у OpenRouter?**
Нет, другой механизм. `google/gemma-4-31b-it:free` уронил уже **минимальный
ping** (429) — размер ни при чём. Тело:

```
google/gemma-4-31b-it:free is temporarily rate-limited upstream ...
"limit_source":"upstream_provider_shared_pool","is_byok":false
```

Это лимит **общего бесплатного пула** OpenRouter (провайдер Google AI Studio),
не наш бюджет и не размер запроса. Заголовков `x-ratelimit-*` OpenRouter в 429
**не прислал вообще** (`rl={}`) — по ним пейсить нечего. Лечится своим ключом
провайдера (BYOK) или роутингом на другого провайдера, не размером/паузой.

Немонотонность (`2048/4000` FAIL, `2048/5000` PASS) — доказательство, что это

Оценка ходит по обе стороны границы → отказ стохастический. `max_tokens=512`
держит резерв заведомо ниже 1000 → 7/7 PASS.

## Две разные 429 — не путать (важно для пейсера)

- **Type A — реальный TPM-троттл (вход).** `remaining-tokens` НИЗКИЙ,
  присутствует `retry-after: N`, `reset-tokens` ~десятки секунд. Виден при
  частых запросах (сконфаундированный smoke: remaining 2097, retry-after 7–29 с).
  Ожидание помогает.
- **Type B — OTPM-отказ (выход), наша боль.** `remaining-tokens=8000`,
  `reset-tokens=1ms`, `retry-after` **отсутствует**. Вход не блокер. Ожидание
  бесполезно. Правится **`max_tokens`**, не паузой.

Диагностический признак Type B в рантайме: 429 **без** `retry-after` и с
`remaining-tokens` == `limit-tokens`. Сейчас пейсер (`providers.py::_pace_if_needed`)
трактует бюджет по входным заголовкам и на Type B будет ждать впустую — это уже
follow-up на код, вне рамок данного аудита.

## Следствия для конфига (не тронуто в этой задаче)

- `max_tokens` в `providers.py::_default_request` сейчас `min(2048, …)` — выше
  OTPM 1000. Именно это, а не `r0_chunk_tokens`, порождает Type B.
- `r0_chunk_tokens` (вход) к 429 отношения не имеет — откат к 4000 безопасен по
  входу (упёрлись бы только за ~12K сумму), но качество чанка это отдельный
  вопрос.

странице Limits в консоли аккаунта, не в публичных доках.
