## 1. Ответственность и процесс

Режим работы — постоянный контракт ведущего разработчика в CLAUDE.md. ChatGPT выполняет доступную работу сам, включая код/тесты/PR; подключение агента только по фактическому блокеру или обязательной независимости QA. Владелец — продуктовые решения, предусмотренные гейты и оценка результата, не оператор терминала.

Каждый пакет: (1) сверить main, точный scope и существующие решения; (2) воспроизвести baseline или описать проверяемый контракт; (3) минимальная реализация и тесты в отдельной ветке; (4) CI и QA по классу риска; (5) исправить только доказанные проблемы, адресно перепроверить; (6) зафиксировать результат, SHA, тесты, ограничения; (7) merge по действующим правилам и следующий пакет. Не повторять полный аудит без установленного триггера. Не ждать завершения всего фундамента, чтобы показать первый полезный UI.

**Режим пакетной автономии (решение владельца 27.11.2026):** выполнять максимально возможное число последовательных разрешённых срезов в одном рабочем цикле по разделу «Последовательная автономная работа пакетами» в CLAUDE.md. Не останавливаться для согласования каждого технического шага; переходить дальше после обязательных проверок и разрешённой интеграции. Пока CI ожидается, брать доступную независимую работу. По окончании цикла — один сводный отчёт со статусами и доказательствами. Остановка только при существенном блокере, новом обязательном гейте, необходимости решения владельца или недоступности дальнейшей работы в текущем сеансе. Все существующие ограничения CODE/MERGE/MEDIA и HIGH QA остаются.

## 3. Продуктовые контрольные точки

- R1 demo: на синтетике открыть проект, посмотреть клип, записать и восстановить вердикт, сравнить версии. Не выдавать за mobile-ready или production. После отдельно разрешённого UI-105 и реальной приёмки — первый полезный пользовательский релиз ревью.
- R2: из интерфейса управлять текущим конвейером, выбрать пресет и отдельные механики, наблюдать задания, экспортировать одобренные клипы. Реальные операции только в утверждённом scope.
- R3: удобный текстовый монтаж и ручные правки с undo/redo и preview, без повторных LLM-запросов без необходимости.
- R4: визуальный редактор и таймлайн, затем слои и расширенная автоматизация. Не задерживать ранние релизы ради функций уровня CapCut.

Названия R1–R4 здесь означают продуктовые контрольные точки, не ревизии документа UI Roadmap R3 и не старые R0–R4 стадии конвейера.

## 4. Когда требуется участие владельца или агента

- Сейчас: принятие PR #33, документационного регламента и отдельный минимальный CODE GO для UI-002/101–102; UI-103/104 после уточнения адаптера.
- Локальное выполнение: только если доступные инструменты не обеспечивают нужный тест/сборку/устройство. Agent task на английском, минимально достаточная модель, evidence в GitHub; без повторного общего аудита.
- Архитектурный совет: при доказанном противоречии контрактов или сложном tradeoff, не для обычных решений. Владелец получает варианты, риски, рекомендацию и конкретный вопрос.
- UI-105, owner media, новые зависимости на gamebox, реальные провайдеры/платные вызовы, публикация, изменения гейтов — только в рамках действующих разрешений. Не открывать FastAPI наружу для удобства.
- Для QA использовать один независимый аудит и адресный recheck по CLAUDE.md; HIGH отдельный протокол. Для документационного PR достаточно проверки diff/ссылок/согласованности; не заявлять runtime PASS без запуска.

## 5. Отчёт и контроль прогресса

По каждому пакету: статус, пользовательский результат, PR/HEAD, доказательства тестов/CI, известные ограничения, следующее действие, OWNER_ACTION только если реально нужен. Не добавлять дополнительные циклы без причины; P3 в backlog. Не обещать сроки без замера возможностей и локального baseline.

На дату подготовки производственный код не изменён. Следующая реализация зависит от принятия R3 и разрешённого scope. Локальные данные, текущий runtime UI, браузерная производительность и безопасность удалённого доступа не проверены в рамках этого документа.
