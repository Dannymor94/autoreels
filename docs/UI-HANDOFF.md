# Авто-Рилс — передача в ветку UI (v3, 2026-10-07)

Документ для чата и агента, которые ведут интерфейс. Заменяет v1 и v2. Разделы 3–6 и 9 — правила, а не пожелания. План работ — в `PLAN-UI.md`.

---

## 1. Что за проект

CLI-инструмент на Python. На входе длинное горизонтальное видео (talking-head, статичная камера), на выходе вертикальные рилсы 9:16. В каждом рилсе: субтитры, заголовок-плашка и монтаж — два плана крупности, перестановка фраз (такты), выделение слов, хвост с уходом в чёрное. Рендер идёт локально на Mac (ffmpeg + `hevc_videotoolbox`). Облако используется только для текста: Whisper и LLM через Groq.

Отбор клипов идёт двумя путями: оценка блоков моделью и ручная разметка строками. Основной путь — ручной, брак 4%. Вся «режиссура» записывается в строке разметки, а дальше конвейер работает детерминированно.

Репозиторий публичный: `github.com/Dannymor94/autoreels`. Агент и чат читают код оттуда. Вне git остаются `reels-out/`, `reviews/` и `data/history.jsonl`.

## 2. Зачем UI

Сейчас цикл такой: экспорт текста → разметка руками или в чате → `--apply` → рендер → QuickTime → вердикт словами в чат → правка. Узкие места:

1. «Какой номер предложения какой текст» сверяется глазами и часто с ошибками.
2. Проверочные рендеры (`_gate/...`) приходится искать по папкам и сравнивать вручную.
3. Каждый вердикт («r05 не договорил») пересказывается словами.
4. Ошибки разметки обнаруживаются только после рендера.

Цель: владелец легко пользуется программой без терминала. Это пункт R2 вехи M1.

## 3. Главный принцип: UI — пульт к манифесту

- **Детерминированность.** Всё, что делается в UI, записывается строкой разметки или полем манифеста: подрезка, правка субтитра, стиль, заставка. Видео UI не трогает никогда. Видео делает только рендер, и из одного манифеста всегда получается одно и то же видео.
- **Автор агентской разметки и автор ручной правки равноправны.** Это одна и та же разметка, только с разными авторами. Агент видит правки владельца как текст и продолжает с того же места.
- **Истину показывает рендер.** Браузерный предпросмотр (субтитры, кроп, обрезка) приблизителен, решения принимаются по рендеру. Отсюда кнопка «проверочный рендер фрагмента».

## 4. Правила расширяемости (алгоритм будет меняться)

1. **UI не знает алгоритма.** Внутренности конвейера (`cloud/`, `local/`, `core/` кроме моделей, `__main__.py`) не импортируются. Всё общение идёт через один модуль-переходник `src/autoreels/orchestr/pipeline_gateway.py`: вызовы `arl … --json` или небольшое публичное API. Конвейер поменялся — правится только переходник.
2. **Конвейер описывает себя сам.** Команда `arl capabilities --json` (её делает основная ветка) отдаёт ключи разметки, метки вердиктов, эффекты с параметрами и диапазонами, пресеты субтитров и схему настроек (из Pydantic-моделей `core/config.py`). UI строит кнопки и формы по этому описанию, не по жёсткому списку. Пока команды нет, переходник отдаёт статический запасной вариант с пометкой `source: "fallback"`.
3. **Версии контрактов.** У манифеста и у каждого `--json`-вывода есть `schema_version`. Если версия незнакома, UI честно сообщает об этом и не рисует мусор. Миграции делает конвейер, а не UI.
4. **Данные владельца не зависят от нарезки.** Номера блоков и предложений зависят от алгоритма сегментации. Вердикты, комментарии, ручные подрезки и правки субтитров привязываются к **времени и словам исходника**: секунды исходника плюс текст слова, а номера хранятся только для справки. Тогда при смене алгоритма их можно перенести автоматически, а не потерять.
5. **Происхождение результата.** Каждый рендер знает, чем он сделан: отпечаток входов, версия кода и хеш настроек (см. п. 7). UI показывает «сделано старым алгоритмом» и предлагает сравнение «старый против нового» в режиме вариантов.
6. **Любое долгое действие — задание.** Применение, рендер, а позже анализ и публикация: у каждого задания id, тип, статус, прогресс, лог, результат. Один экран заданий на все типы.
7. **Экраны — модули.** Список экранов задан в одном месте. Экран показывается, только если `capabilities` сообщает, что функция есть.

### Заложено под многопользовательность (не строим, но не мешаем)

- Каждая запись (вердикт, правка) содержит `author` и базовую версию объекта. Правка к устаревшей версии не перезаписывает чужую, а возвращает конфликт.
- Ручные правки хранятся журналом действий. Манифест = исходный манифест + журнал. Отсюда история, отмена и авторство. Агент — тоже автор (`author: "agent"`).
- У клипов постоянные ID, не зависящие от номера `r*` и пути к папке (см. п. 7: проверить, стабильны ли номера сейчас).
- Для браузера делается лёгкая копия в H.264. HEVC-оригинал Chrome и Firefox часто не воспроизводят.
- Позже, не сейчас: вход и роли, база вместо файлов, сетевой доступ, очередь с несколькими исполнителями (вторая машина — Windows), публикация в crosspost.

## 4a. Рабочие копии: код отдельно, данные отдельно

- Основная программа и все данные — `~/Documents/autoreels`. Параллельные ветки — соседние папки (`autoreels-publish`, `-verify`, `-bench`, `-score`). Ветка UI — `~/Documents/autoreels-ui`.
- Рабочие копии делят историю git, но **не данные**: `reels-out/`, `reviews/`, `data/`, исходники есть только в `~/Documents/autoreels`.
- **Код UI** правится только в `autoreels-ui`.
- **Данные** UI читает из корня, заданного настройкой `AUTOREELS_ROOT` (по умолчанию `~/Documents/autoreels`), а не из папки, где запущен сервер.
- **Команды конвейера** (`arl blocks`, `arl render`) UI вызывает из `AUTOREELS_ROOT`, его интерпретатором. Иначе запустится устаревшая копия конвейера из ветки UI.
- **Запись** в `AUTOREELS_ROOT` только в `reviews/verdicts/`, `reviews/edits/` и через `--apply`. Всё остальное — только чтение.
- Разработка и тесты агента идут на **демо-источнике** внутри `autoreels-ui` (`AUTOREELS_ROOT=./demo`). Настоящие данные агент UI не трогает.
- После слияния в `main` код и данные окажутся в одной папке. Настройка просто укажет на неё же.

## 5. Формат вердикта (согласован)

Файл `reviews/verdicts/<stem>.jsonl`, одна строка JSON на действие. Только дописывается, никогда не переписывается.

```json
{"schema_version": 1,
 "ts": "2026-10-07T10:12:03+03:00",
 "author": "anton",
 "stem": "2026-08-08 11h 42m 49s",
 "clip": "r05",
 "clip_uid": null,
 "variant": "_gate/montage",
 "file": "reels-out/2026-08-08 11h 42m 49s/_gate/montage/r05.mp4",
 "render_ref": {"fp": "<fingerprint из r05.render.json>", "mp4": "<размер + sha1 первого и последнего МБ>"},
 "verdict": "issue",
 "tags": ["fade_on_word"],
 "at": 41.2,
 "src_at": null,
 "comment": "затухание на «принятие»"}
```

- `variant`: `""` — основной рендер, `_gate/<имя>` — проверочный.
- `verdict`: `ok` | `issue` | `note` | `choose`.
- `render_ref`. Сейчас `render.json` содержит только `{"fingerprint": …}`: хеш входов, без версии кода и без планов `c:` и хвоста. Поэтому актуальность вердикта проверяется по `mp4` (частичный хеш файла), а `fp` хранится для справки. После перерендера вердикты с другим `mp4` считаются устаревшими.
- `tags`: `cut_word`, `foreign_speech_tail`, `fade_on_word`, `thought_unfinished`, `start_cut`, `start_context`, `ends_on_filler`, `jump_cut`, `flicker`, `squashed_frame`, `video_freeze`, `av_desync`, `subtitle_mismatch`, `keyword_missing`, `tail_unnatural`. Неизвестные метки сохраняются как есть, UI показывает их серым. Подписи в UI русские. Список берётся из `capabilities`, этот перечень — запасной вариант.
- `at`: секунда внутри клипа. `src_at`: секунда исходника. Заполняется, когда основная ветка отдаст карту времени (п. 7), до тех пор `null`.
- `clip_uid`: `null`, пока основная ветка не введёт постоянные ID.
- Запись выбора варианта:
  ```json
  {"verdict": "choose", "clip": "r05", "variant": "_gate/m18_synth",
   "against": ["_gate/montage", ""],
   "refs": {"_gate/m18_synth": {…}, "_gate/montage": {…}, "": {…}},
   "comment": "стоп-кадр естественнее"}
  ```
  `refs` нужен, чтобы выбор устаревал после перерендера любого из вариантов. Записи выбора не влияют на статус клипа «ок / правки».
- Запись закрытия гейта (вместо «гейт закрыт» словами в чате):
  ```json
  {"verdict": "gate", "gate": "_gate/montage_p2", "result": "accepted",
   "comment": "все швы ок, r03 хвост смотреть ещё раз"}
  ```
  `result`: `accepted` | `changes`. Агент основной ветки читает последнюю такую запись по папке гейта.
- Как агент читает файл: по каждой паре клип+вариант берутся записи с актуальным `render_ref.mp4`. Последняя `ok` означает «принят». Все `issue` — это список правок.

## 6. Экраны и порядок

Каждый шаг — то, что владелец трогает руками. После шага идёт просмотр владельцем, только потом следующий.

1. **Просмотр + вердикты.** Список клипов источника со статусами (принят / замечания / не смотрел / перерендерен и ждёт пересмотра). Вертикальный плеер, вкладки вариантов с переключением на той же секунде, метки клавишами 1–9, Enter = «ок» и следующий клип, J/K — соседний клип, засечки замечаний на шкале.
2. **Сравнение вариантов рядом**, 2–3 синхронно, с записью выбора.
3. **Текст клипа и ручная подрезка.** Текст с вошедшим, вырезанным, границами и тактами. Клик по слову — граница, точная подгонка по волне звука с шагом в кадр и привязкой к паузам. Строка разметки собирается под текстом автоматически. Предпросмотр: первые и последние слова, порядок тактов, предупреждения. Требует от основной ветки границ с точностью до слова (п. 7).
4. **Субтитры.** Правка текста как поправка к слову в манифесте, а не в `.ass`. Стили — пресеты (шрифт, размер, отступ, обводка, цвет выделения) на источник или клип, с переопределением полей.
5. **Заставка и концовка.** Библиотека готовых роликов: приводятся к формату рилса при добавлении, ссылки по хешу файла. Порядок: заставка → клип → хвост → концовка. Решить, как концовка заменяет уход в чёрное.
6. **Эффекты.** Каталог из `capabilities`. Первым в него переезжает существующий наплыв. Произвольные фильтры ffmpeg в UI не открываются.
7. **Очередь заданий.** Рендер в проверочную папку, статус, лог, одно задание на папку за раз.

Позже, не в этой ветке сейчас: публикация в crosspost (граница — принятый рендер с вердиктом `ok` на этом `render_ref`; ключ идемпотентности клип + рендер + профиль; копия для публикации в `h264_hq`). Обложки заморожены: обложка = кадр в момент плашки.

## 9. Правила ветки UI

- Ветка `ui`, отдельная копия: `git worktree add ../autoreels-ui -b ui`.
- Код UI только в `src/autoreels/orchestr/` (API, переходник, задания) и `ui/` (фронтенд). Конвейер не правится. Нужно изменение — задача в основную ветку.
- Python-зависимости UI в `ui/requirements.txt` (FastAPI, uvicorn, watchfiles, filelock). `pyproject.toml` основной ветки не трогается.
- UI не пишет в `manifests/` напрямую, только через `--apply`. Файлы ответов — с резервной копией. Из `reels-out/` ничего не удаляется, кроме явно выбранного владельцем.
- Всё локально, видео отдаётся с диска с поддержкой HTTP Range (без неё в Safari не работает перемотка). Никаких ключей во фронтенде.
- **Стек (решено):**
  - сервер — Python, FastAPI + uvicorn, только `127.0.0.1`; вся логика (проверки, предупреждения, подсказки, расчёты) — на сервере, под pytest;
  - экран — React + TypeScript, сборка Vite; данные с сервера — TanStack Query; стили — обычный CSS с переменными темы, без дизайн-библиотек;
  - типы API генерируются из моделей сервера: FastAPI отдаёт OpenAPI → `openapi-typescript` → `ui/src/api/types.gen.ts`. Сборка падает, если сервер и экран разошлись. Сгенерированный файл не правится руками;
  - волна звука — wavesurfer.js; субтитры в черновике — JASSUB (libass в WebAssembly), после проверки со шрифтами рендера; иначе HTML с пометкой «приблизительно»;
  - тесты — pytest + `TestClient` (сервер), Vitest (компоненты), Playwright (сценарии, позже);
  - Node нужен только для разработки. Собранный экран (`ui/dist/`) отдаёт FastAPI, для использования Node не нужен.
- Запуск: `python -m autoreels.orchestr` (порт 8765, открывает браузер). Алиас `arl ui` добавляется задачей в основной ветке.
- **Безопасность:** файлы отдаются только из `AUTOREELS_ROOT/reels-out/` и папки кэша; любой путь нормализуется и проверяется на выход за эти корни (`../`), тест на это обязателен.
- **Кэш копий** (H.264 рендеров и исходников для черновика, пики волны): одна папка `AUTOREELS_ROOT/data/cache/ui/` (уже в `.gitignore` основной ветки), пересоздаётся. В UI — кнопка «очистить кэш» и показ занятого места. Копия исходника ≈ 1 ГБ на час записи.
- **Работа рядом с агентом основной ветки:** UI видит `.render.lock` и не запускает второй рендер в ту же папку; изменения на диске (`watchfiles`) обновляют экран сам.
- **Поддерживаемость:** экран ничего не вычисляет; любое действие — команда `{type, …}` в одну точку API (модель Pydantic + обработчик + журнал); всё перечислимое (клавиши, метки, подписи, экраны) — таблицами в одном месте; один компонент — один файл до ~200 строк; рецепты «как добавить экран / команду / метку» в `ui/README-AGENT.md`; версии зависимостей зафиксированы (`package-lock.json`, `ui/requirements.txt`).
- После этапа U3 (см. `PLAN-UI.md`) UI сливается в `main`, дальше — короткие ветки на задачу. Недоделанные экраны прячутся флагом.
- `pytest` основной ветки остаётся зелёным, тесты UI отдельно. Тесты не запускать во время рендера.
- Ребейз на `main` после каждой вехи основной ветки. Слияние — после просмотра MVP владельцем.
- Задачи агенту — в постоянном формате: проверка ветки → пронумерованные части с тестами и коммитом → «зачем» → конкретные шаги → список НЕ МЕНЯТЬ → условия остановки → отчёт по шаблону → `IMPLEMENTED, GATE PENDING`.

## 10. Узкие места использования и как их снять (UX)

Порядок — по тому, сколько времени владельца съедает проблема.

**10.1. Ожидание рендера.** Главная потеря: цикл «правка → рендер → просмотр» длится минуты.
- **Черновой просмотр без рендера.** Плеер проигрывает H.264-копию исходника, перескакивая по окнам манифеста. Субтитры и плашка рисуются HTML поверх. Подрезка и перестановка тактов видны мгновенно. Это приближение (кроп, наплывы и хвост — только в рендере), так что честно подписано «черновик».
- **Проверочный рендер фрагмента:** только ±3 с вокруг правки, а не весь клип.
- Рендер идёт в фоне, а владелец продолжает смотреть следующие клипы. Готовый перерендер помечается в списке.

**10.2. Ошибки видны поздно.** Многие дефекты из списка меток видны ещё в тексте, до рендера.
- **Проверка разметки на лету:** предупреждения прямо в тексте клипа. Конец на слове-паразите («…понятно?»), начало без контекста («Это…», «То…»), граница внутри слова или без паузы, клип длиннее лимита площадки, слишком короткий план. Источник — предупреждения `--dry-run --json`. Цель — чтобы до рендера доходили только визуальные дефекты.

**10.3. Видео и текст живут отдельно.**
- Клик по слову перематывает плеер. При воспроизведении подсвечивается текущее слово.
- Увидел дефект в видео → одна клавиша открывает текст на этом месте с курсором на текущем слове.

**10.4. Вердикт не превращается в исправление.**
- У частых меток есть **детерминированные подсказки-исправления** одним кликом: «обрезано слово» → «сдвинуть конец к следующей паузе»; «начало без контекста» → «начать с предыдущего предложения»; «конец на слове-паразите» → «отрезать хвостовое предложение». Подсказка — это предложенная правка разметки, её видно до применения.
- Что не решается подсказкой, уходит агенту через файл вердиктов.

**10.5. Непонятно, что требует внимания.**
- **Главный экран — «входящие»:** перерендеренные клипы, ждущие пересмотра; новые источники; упавшие задания; что отдано агенту и что от него вернулось.
- После перерендера по замечанию клип открывается сразу в режиме «было / стало» рядом.

**10.6. Страх сломать.**
- Видимая история правок клипа с отменой любого шага. Перед применением показывается разница «что изменится в разметке».
- Массовые действия («принять все без замечаний», «пресет на весь источник») с подтверждением и отменой.

**10.7. Язык и обучение.**
- В интерфейсе человеческие слова: «начало», «конец», «вырезать», «крупный план». Строка грамматики видна вторым планом, для агента и для проверки.
- Подсказка по клавишам на `?`. UI запоминает, где владелец остановился: источник, клип, секунда.

**10.8. Лимиты площадок на виду.** Таймер длительности клипа с порогами, наглядная зона обрезки сетки профиля 3:4. Проверить один раз, не срезается ли плашка.
