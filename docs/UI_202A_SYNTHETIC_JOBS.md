# UI-202A — synthetic queue

First durable job slice after UI-201, no real executor. Disabled by default. Supported launcher opt-in: python -m autoreels.orchestr --root <existing-isolated-test-root> --synthetic-jobs --no-browser. Do not run against owner media; no pipeline calls, media reads or output, transfers, providers, fees, subprocess or legacy state writes. The queue is a separate .ui-synthetic-jobs.sqlite3 inside the explicit test root. GET /api/jobs returns enabled=false when off, no disk access. PUT /api/jobs/{job_id} accepts only explicit synthetic create/cancel. Stable UUID binds the same immutable target mode/outcome; exact retries return current state, mismatch 409. No inferred target, no fallback. Existing auth and origin/body protection applies. Up to 100 retained records; no automatic deletion.

One FIFO active job. Each tick is one SQLite BEGIN IMMEDIATE transaction: queued → prepare → plan → simulate_render → success/failed, or empty at plan; cancel is atomic and terminal. Progress is simulated, not measured. On restart a fresh process continues committed checkpoints; no external effect can be replayed. A repeated demo uses a new ID, cancellation retries reuse the old ID. UI polls active test mode, displays status, stage, progress and target; reload reads DB; unknown mutation result allows exact retry within the screen. No promise of automatic recovery from corrupted/unavailable storage; errors block rather than redirect. Worker logs generic error only. Production executor requires lease/fencing, external output lock, immutable full plan, explicit target ID, permission checks, retry policy and artifact reconciliation; not implemented. QA: deterministic state transition, duplicate/cancel, restart via reopened DB, serialization, empty/failed, no fallback, bounded history, auth and symlink; focused browser create/cancel/reload mock; existing CI. No separate independent audit for reversible synthetic-only operations.
