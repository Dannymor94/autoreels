# gamebox: общий замок тяжёлых задач и расшифровка диктофона

## Замок (M108)
На gamebox работают две тяжёлые вещи: llama-server (Qwen3-27B, ~12 ГБ памяти и 8 потоков) и озвучка книги (модель 1.7B, 11.6 ГБ на воркер и все 16 потоков). Одновременно они не помещаются. Поэтому обе стороны берут один замок: `flock` на файл `heavy_lock.path` (`config/r0.yaml`, по умолчанию `/mnt/data/locks/heavy.lock`). Кто пришёл вторым, ждёт и не обрывает чужую работу.

- **autoreels** берёт замок, когда нужна локальная модель (`--llm local`) или whisper.cpp на gamebox (`arl dictate`, `arl tx-compare`, `--tx local`). Если llama-server выключен, autoreels сам его запускает и ждёт загрузки модели, а в конце останавливает — только если запускал сам. С `--llm auto` локальная модель — запасной вариант: замок берётся без ожидания, а если gamebox занят, работа идёт через облако.
- **Озвучка** запускается через свою обёртку (репозиторий audiobook): берёт тот же замок, останавливает llama-server, в конце поднимает его снова, если он был запущен до неё.
- Замок держит процесс `ssh gamebox flock … cat`: он живёт, пока жив процесс autoreels. Если процесс упал, замок освобождается сам.
- `arl gamebox` показывает, свободен ли замок, работает ли llama-server и сколько свободно памяти. `arl gamebox take` берёт замок (дожидается) и сразу отпускает — проверка, что замок работает.
- `heavy_lock.host: ""` — замок выключен, всё работает как раньше.

## Диктофон (M109)
`arl dictate [файл …]`. Без файла команда спросит путь; файл можно перетащить в окно терминала.
- Проверяет, что gamebox отвечает. Если нет — предлагает Groq (`--groq` — сразу через Groq).
- Расшифровывает через whisper.cpp на gamebox (`config/transcribe.yaml`, раздел `whispercpp`). Перед этим берёт замок: если идёт озвучка, ждёт её конца.
- Текст с абзацами по паузам кладёт рядом с аудио — `<имя>.txt` (`--format srt|vtt|json` — другие форматы). На Mac текст ещё и копируется в буфер обмена (`--no-copy` — не копировать).
- Результат кэшируется по содержимому файла: тот же файл второй раз расшифровывается мгновенно.

## Рендер на видеокарте (M156)

Видеокарта RX 580 кодирует HEVC/H.264 через VAAPI (Mesa, пакет `mesa-va-drivers`; проверка — `vainfo`, строки `VAEntrypointEncSlice`). Пользователь рендера — в группах `render` и `video`. Кодер `--encoder hevc_vaapi` или `h264_vaapi`. Каждая команда ffmpeg с таким кодером получает `-vaapi_device` (по умолчанию `/dev/dri/renderD128`, иначе env `RENDER_VAAPI_DEVICE`), загрузку кадров в GPU в конце видеофильтра (`format=nv12,hwupload`) и не получает выходного `-pix_fmt` (`local/render.py _hw_argv`). Субтитры (`ass`), кроп и цвет считаются процессором, кодирование — видеокартой. Скорость задаёт `-rc_mode VBR` (M158: без режима RX 580 кодировал с постоянным QP и не держал битрейт профиля — 7,0 Мбит/с против 4,9 у videotoolbox). Остальные кодеры не меняются. Пробный кадр не прошёл — рендер берёт запасной кодер, как при AMF. Рендер на gamebox — тяжёлая задача: запускать под общим замком (`flock /mnt/data/locks/heavy.lock .venv/bin/python -m autoreels render …`), озвучка книги ждёт его или он её.

**HEVC на RX 580 не годится (M160).** На длинных клипах `hevc_vaapi` выдаёт кадры с ошибками в самих данных (`CABAC_MAX_BIN`): в QuickTime — зелёные блоки до следующего ключевого кадра; перепаковка и режимы скорости не помогают, 10-секундные пробы чистые. `h264_vaapi` — 0 ошибок. Поэтому gamebox рендерит в H.264 (профиль `h264`).

## Рендер с Mac на gamebox (M161)

`arl render --manifest reviews/<копия>.review.json --gate <имя> --remote` или `arl auto <источники> --remote`. Mac отправляет на gamebox (`config/render.yaml remote:`, папка `/mnt/data/autoreels`): отслеживаемый код (`git ls-files`), копию разметки, `transcripts/<источник>.*`, кэшированную расшифровку источника из `data/cache/` (без неё рендер там проверяет швы грубым правилом и печатает ложные «seam inside word» — m158, m160), модель лиц и музыку; исходник — только если gamebox не находит его по содержимому. Рендер идёт там под общим замком с кодером и профилем из `remote:`, папка гейта возвращается на Mac (`tar` по ssh: в именах источников бывают пробелы). Только в гейт: настоящие клипы с другой машины не пишутся. Окружение там: `/mnt/data/autoreels/.venv` (`pip install -e ".[dev]"`, OpenCV обязателен — без него рамка не по лицу).

## Проверка целостности клипа (M179, M180)
В m165 на gamebox 16 клипов из 26 упали с `integrity check failed — missing picture in access unit with size 12`, и проверка их удаляла, так что разобрать файлы было нельзя. Замер m179: 41 клип `h264_vaapi` и пробное кодирование — ни одного такого сообщения, маленьких пакетов в файлах нет; причина не найдена. С M180 клип, не прошедший проверку, остаётся как `rNN.ERROR.mp4`, слова ffmpeg — в `rNN.integrity.txt` рядом: если сообщение вернётся, файл разбирается (`ffprobe -show_packets`, `-bsf:v trace_headers`), и правка делается по нему.

**M212c.** m212 нашла `prew_isaev_anna/_gate/ab192/r03.integrity.txt` (h264, gamebox, 30.10 11:22) рядом с чистым `r03.mp4` (hevc, Mac, 11:40): успешный перерендер удалял старый `.ERROR.mp4`, но оставлял его `.integrity.txt` — и сам сбойный файл снова потерялся. Теперь у каждого `rNN.ERROR.mp4` есть `rNN.error.txt` (когда, на какой машине, каким кодеком, все причины), а чистый перерендер переносит прежние `rNN.ERROR.mp4`, `.error.txt`, `.integrity.txt` в `_errors/rNN.<время>.*`: в папке гейта — только текущее, улики целы. Разбор файла: `sh handoff/m179/probe_au.sh <клип>`.

**M212d — причина найдена и лечится.** m212c разобрала сохранённый на gamebox `ab192/r03.ERROR.mp4`: `h264_vaapi` поставил на место одного кадра пакет в 12 байт только со служебным SEI (NAL 6), на 54,9 с из ~68,7 — 4120 пакетов, 4119 кадров, полный декод: «missing picture», «no frame!». Тревога не ложная — кадр потерян. Сбой плавающий (m165: 16 из 26, m179: 0 из 41, ab192: 1). `render.yaml vaapi_soft_retry: true`: такой клип (`.ERROR.mp4` + «missing picture in access unit» в `.integrity.txt` + `*_vaapi` в `.error.txt`) рендерится ещё раз программным кодеком (`h264_vaapi` → `libx264`, `hevc_vaapi` → `libx265`), сбойный файл уходит в `_errors/`, в `rNN.render.json` — `encoder_retry`. Другие ошибки и другие кодеки — как раньше.

## SSH до gamebox: «No route to host»
До SSH дело не дошло — Mac не видит адрес в локальной сети. По порядку: (1) VPN на Mac перехватывает локальную сеть (2026-11-02: перезапуск VPN вернул доступ) — в VPN включить «Allow LAN access» или исключить `192.168.3.0/24`; (2) macOS 15 не дал приложению (Terminal / iTerm / Claude / VS Code) доступ к «Локальной сети» — Настройки → Конфиденциальность → Локальная сеть; (3) gamebox получил другой IP — `ip -4 addr` на gamebox, закрепить адрес в роутере; (4) Mac в другой сети — `ipconfig getifaddr en0` должен быть `192.168.3.x`.

## Карта говорящих (M165, M170)

`arl speakers <источник>` — кто когда говорит (pyannote, `tools/diarize.py`) → `transcripts/<источник>.speakers.json`. Модель — в отдельном окружении с torch (на Mac `~/.venvs/m141`, `config/r0.yaml autocut.speakers_python`), токен Hugging Face — `HF_TOKEN` в `.env` (условия моделей `pyannote/speaker-diarization-3.1` и `pyannote/segmentation-3.0` приняты). `arl auto` строит карту сам, если её нет (`autocut.speakers_auto`); не вышло — прогон идёт без неё.

## VPN для autoreels на gamebox (M214b)
На gamebox нет системного VPN, а облачным моделям (Groq, OpenRouter, Hugging Face) он нужен. Xray (VLESS, закреплён 26.10.31, `~/.local/xray/`) работает как служба пользователя `systemd --user` (`xray.service`, linger включён — живёт без входа) и даёт локальный прокси: http `127.0.0.1:10809`, socks `127.0.0.1:10808`. Система через него не ходит — только autoreels: в `.env` gamebox `HTTPS_PROXY`/`HTTP_PROXY=http://127.0.0.1:10809`, а `NO_PROXY` — Яндекс (Диск качается напрямую) и localhost. Маршруты повторяют клиент владельца: `domain:ru`, `domain:su`, `domain:xn--p1ai`, `geosite:category-ru`, `geoip:ru`, `geoip:private` — напрямую.

- Ключ — `~/.config/xray/vless.txt` (chmod 600), в git и в задачи не попадает. Конфиг — `python tools/vless2xray.py ~/.config/xray/vless.txt --out ~/.config/xray/config.json` (chmod 600), проверка `~/.local/xray/xray run -test -c ~/.config/xray/config.json`.
- Сменить ключ: заменить строку в `vless.txt`, пересобрать конфиг, `systemctl --user restart xray`.
- Проверка: `curl -s -o /dev/null -w "%{http_code}" -x http://127.0.0.1:10809 https://api.groq.com/openai/v1/models` → 401 (дошли, ключа в запросе нет); без прокси — нет ответа или 403.

## Весь прогон на gamebox (M214c)
`arl auto <ссылка Я.Диска или папки> --on-remote --no-render` — Mac проверяет gamebox, отправляет код (`git ls-files`, как M161), ставит метку `.arl/auto-mark` и выполняет ту же команду там через `ssh -t`: вопросы об удалении исходников — в терминале Mac. Видео скачивается и живёт на gamebox (`/mnt/data/autoreels/inputs`), модели идут через прокси (раздел выше), Яндекс — напрямую. После прогона на Mac возвращаются только тексты, изменённые прогоном: `manifests/`, `transcripts/`, `reviews/`, `exchange/` (tar по ssh). Пути Mac (`--root`, `--cache-dir`, `--inputs-dir`) на gamebox не передаются. Выравнивание на gamebox — `torch 2.15` / `torchaudio 2.11` (под Python 3.14 закреплённой 2.8.0 нет), на Mac — 2.8.0: источник обрабатывается целиком на одной машине. Кэш ответов моделей (`data/cache/llm/`) у каждой машины свой. **M215:** файлы `exchange/*.scenario.answer.txt`, написанные на Mac, уезжают на gamebox перед прогоном, а задание сценариста (`*.scenario.md`), написанное прогоном, приходит на Mac — в конце печатается, что с ним делать. Сценарист через чат работает с `--on-remote` без `scp`. Рендер там — по конфигу рендера gamebox; в текущей фазе — `--no-render`.
